# 门：判据逐条、加一条规则、诱饵

**什么时候读它**：你要改 `lib/check.mjs` 的判据、要**加**一条新规则、
或者某条判据红了而你怀疑是判据自己的问题。

判据的实现只有一处：`lib/check.mjs` 的 `judge()`（正文 → 失败清单）。
规范侧的家是 `SPEC.md` §6 —— **两边必须一起改**（改判据 = 改规范）。

## 一、G1–G8：每条抓什么失败模式

| # | 判据 | 它抓的失败模式 |
|---|---|---|
| **G1** | frontmatter 三字段齐全；`name` == 目录名；都是单行标量 | skill 加载不到（harness 只认这三个字段） |
| **G2** | 体量预算（400 行 / 20 KB / 代码块 ≤15 行 / 表 ≤12 行）+ **行尾必须 LF** | 一次塞太多 → token 成本；CRLF → frontmatter **静默失效** |
| **G3** | 正文**行内代码**里的路径必须存在（按三个根查，见 `references/roots.md`） | 死链：读者点过去一片茫然，而写的人以为它还在 |
| **G4** | 命令里引用的脚本路径必须存在（`tools/` `npm/` `examples/` `docs/` `vendor/`…） | 命令复制过去跑不了 —— "确切命令"是收录判据之一 |
| **G5** | `@html.` / `@style.` / `@cmd.` / `@sub.` 的 API 名必须在源码里存在 | 编出来的 API（AI 最容易犯）：读者照抄 → 编译错 |
| **G6** | 文档链接的 `§N` 节号必须真的存在 | 指向一个不存在的节 —— 静默，而且会让人以为整份文档都相关 |
| **G7** | 禁语表（`claims.txt`）出现即红 | **把"未做"写成"已支持"** —— 这条是这套东西存在的理由 |
| **G8** | 体量 / 条目数指纹变了就红（`skills.lock.json`） | 悄悄膨胀：200 行变 380 行没人看过 |

## 二、判据背后的三条设计原则

1. **宽进严出（G3 有"行文残留"那条）**：`docs/FINDINGS.md的补记` 这种尾巴允许，
   去掉尾部的非路径字符后再查一次 —— 因为**误杀比漏报更伤**：
   人看到红的处置通常是"把真引用删掉"，那正是最坏的结果。
2. **三个候选根都认**：内容仓根 / 程序根 / 那个 skill 自己的目录。
   只认一个根会让另两边全红（见 G3 的实现注释）。
3. **不许有"静默不查"**：判据白名单之外的东西等于没判据。
   曾经的洞：`bin` / `lib` / `grammars` 不在白名单 ⇒ 内容里讲程序的指针**一个都没查过**
   （不是"查了但错了"，是"根本没查"）—— 现在有诱饵 `bad-program-path` 守着。

## 三、加一条新规则：固定四步

1. **写判据**：加进 `judge()`（或像 `docfacts` / `verify-site` 那样独立成门）。
   出口一律 `process.exitCode`，**别调 `process.exit()`**（会被上游吞掉）。
2. **配诱饵**：在 `--selftest` 的 `cases` 里加一条**必须被点名**的假样本。
   ⚠️ 判据没诱饵 = 没加：没人能证明它真的会红。
3. **改规范**：`SPEC.md` §6 的表加一行（判据 + 抓什么），与实现同一次提交。
4. **落指纹**：如果判据让某些 skill 的体量/结构变化，跑 `--update-lock <名字>` 复核落锁。

加完两边都要过：`check --selftest`（诱饵全被点名、正例不许被误杀）
**和** `check`（真实内容不许被误杀）。

## 四、诱饵清单（`check --selftest`）

现在的诱饵按"每条判据一个"摆：名字不匹配 ｜ 缺字段 ｜ 没有 frontmatter ｜ 体量超限 ｜
代码块超长 ｜ 假路径（内容仓侧）｜ 假路径（程序侧 `bin/…`）｜ 假脚本（G4）｜
编造的 API（G5）｜ 不存在的节号（G6）｜ CRLF ｜ 禁语（G7）。

最后还有一个**正例**：它必须**一条都不红** —— 只有诱饵全中、正例全过，才说明门是"能分辨"的，
而不是"见谁都红"。

## 五、落锁（G8）的政策

- 指纹算的是 `SKILL.md` / `references/**` / `FAQ.md`（**`scripts` 子目录不进指纹**）：
  随 skill 一起发的工具天天改，不该天天触发"人复核"。
- 指纹变了 → **硬红**（不是提示）：提示会被淹没，而这条门的全部意义就是"不许悄悄膨胀"。
- `--update-lock <名字>` 的语义是"我**看过**这次变化"；**不是**让门变绿的手段。
- **只锁一个**：整文件重写会把别人正在改的那份的指纹一起锁掉，他改完 G8 就无辜地红。
- **锁是一份，但记根**：程序可以面对多个内容根（内容仓的 `.agents/skills` 与程序自己的
  `.dsh/skills`），锁跟着程序走；每条指纹记着**它属于哪个内容根**，
  于是查 A 根不会把 B 根报成"已删除的 skill"（提示一多，真提示就被淹了）。
- `--update-lock` **出现在参数里任何位置都认**：曾经它必须是第一个参数，
  于是 `check --skills <根> --update-lock` 静默退化成一次普通检查 —— 以为落了锁，其实没落。

## 六、另外两道门（形状不同，别混）

| 门 | 它查什么 | 它的"真值"从哪来 |
|---|---|---|
| `docfacts`（`facts`） | 内容仓的文档有没有撒谎（版本号、状态、"未做"清单…） | **只查能从代码算出来的**事实；分**硬 / 软**两档；豁免必须写在文档里 |
| `audit`（`highlight.mjs --audit`） | 代码上色坏没坏（召回率 / 漏色比例） | 纯正则数出的"必须上色的词法元素"（关键字 / 字符串 / 注释 / 数字） |
| `verify`（`verify-site.mjs`） | 站点真的是那样吗（真 Chrome + CDP 真鼠标） | 从**内容源现取**探针（不写死在脚本里） |

`docfacts` 的设计与已知边界在 `DRIFT.md`；`verify` 的判据清单的家是**它自己的文件头**
（一张表：每条断言抓哪个失败模式）。
