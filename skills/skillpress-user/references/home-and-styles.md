# 首页怎么写、样式与构造怎么改

> ⚠️ **已定要改（D19/D20，还没落地）**：首页的内容源要改成 `skillpress/WEBSITE.md`，`SKILL.md` 只讲工具本身 —— 今天仍读 `SKILL.md`。

**什么时候读它**：你在排首页（顶栏栏位、下拉菜单、纯链接节），
或者要把站点换成自己的配色 / 字号，要加一块**新构造**（图片、折叠、卡片…）。

## 一、首页就是一份 skill（有它自己的规矩）

| 你写的 | 站点上变成 |
|---|---|
| H1（`# 标题`） | **站名**（顶栏左边）+ 首屏大标题；它**不进正文** |
| 首个 `##` 之前的段落 | 首屏引言（`lede`） |
| `## [名字](目标)`（**整条**是链接） | 顶栏**一条导航** —— 点了**跳页**，直接渲染目标那一份 |
| 普通 `##`（不是链接） | ⚠️ **不进顶栏**；正文今天**也不上首页**（缺口）：写进首屏，或做成一页再用链接节指过去 |
| `###` / `####` | 正文里的章节标题；只有 `##` / `###` 进**右栏本页目录** |

三条会咬人的（都吃过）：

- **顶栏只画"点了真会到某处"的**：结构性三条（首页 / 书架 / 搜索）+ 首页里**带目标**的那些 `##`。
  顶栏是**一行**，栏名要短（序号会被剥掉），7 个长标题会把它挤爆 —— 细则放正文第一句，别写进标题。
- **纯链接节的判定很严**：只有 `[名字](目标)` 占满**整条标题**才算；正文里有链接**不算**。
  目标是相对**首页那份 skill 的目录**解析的，**认不出来就报错**（不给你一个静默的死链）。
- 纯链接节如果**还带着正文**，生成器会提示"点它会跳到 X"—— 那条正文只在"不跳"时才看得到，
  想让它真的显示就别把标题写成链接。

## 二、markdown 支持的构造（刻意窄）

正文块：标题（`##`–`####`）、段落、列表、表格、围栏代码块、引用、分隔线，
以及**独占一行的图片**（`![alt](x.png)` 单独占一行 ⇒ 收成真 `<img>`；`press` 会把图拷进 `img/`）。
行内只认三样：`` `code` ``、`**bold**`、链接。

两条刻意的边界：

- **不认识的构造逐条点名报错**（行首原始 HTML、表格缺分隔行、围栏没闭合…），**不静默丢内容** ——
  "解不开的必须看得见"；生成器报错时 `--check` 也一起红。
- **链接按"台词"渲染**（这是静态阅读页，没有路由）：文字与目标相同时只留一份；
  否则渲染成"文字 + 代码样式的路径"。

要加**折叠 / 卡片**这类新构造：解析边界与渲染是**两边**的事，见第四节。

## 三、改外观：配色、字号、代码颜色

配色与字号**都在程序包里**（⚠️ **不在**实例的 `app.mbt` —— 那里只剩接线）：

| 文件 | 管什么 |
|---|---|
| 程序的 `shell/tokens.mbt` | **设计 token 的唯一来源**：色值只在最底层的"原语"里写死；上面是语义色（`Palette`：一个用途一个名字，如 `indigo_light` / `paper_light`）、再上面是明暗不变量（间距 / 字号 / 行高 / 圆角，如 `fs_base` 15.5、`fs_h1` 30.0） |
| 程序的 `shell/theme.mbt` | 把 `Palette` 按明暗（`Scheme`）与三态偏好（`Pref`）组装成 `Theme` **值**，跟着 Model 走；上色色号的翻译在 `Theme::tok_color` |

铁律是"**渲染代码里不许出现字面色号**"：组件只引用语义名，换皮才只改一处。
（⚠️ 以前那份"在 `app.mbt` 顶部改一组 `c_bg` / `c_ink` / `c_head` 常量"的写法**已经过期**：
那些常量不存在了。）

**代码块的颜色是另一条链**：色号（调色板的索引）由程序 `engine/highlight/hl.mbt` 决定，
而"这个色号长什么样"由 `app.mbt` 的 `tok_color` 决定 —— **索引两边对齐，改要一起改**，
错位不会报错，只是颜色悄悄变了。

⚠️ 样式层的坑（改样式前值得知道）：这套界面是 moobile 的样式系统，
RN 上有几条"写了不报错但没效果"的陷阱（按下一类、`transform` 每项只读第一个键、
`position: sticky` 连构造器都没有、`View` 不滚动）。这些的家是内容仓 moobile 那份讲坑的
`moobile-pitfalls` skill，别在这儿重抄。

## 四、加一块新构造 = 两边一起改

| 这边 | 改什么 |
|---|---|
| 程序侧 `engine/content/blocks.mbt` | 解析：把 markdown 里的新写法变成类型化数据（`Block` / `Span` 的新分支） |
| 实例侧 `app.mbt` | 渲染：`block_view` 里给新分支写画法（现成 8 种：标题三档 / 段落 / 引用 / 代码块 / 列表 / 表格 / 分隔线） |

只改一边的症状：解析出来了但页面不显示（`match` 穷尽性会提醒 app 侧），
或者渲染没数据可渲。**生成物是两边共用的契约**（`content/content.generated.mbt`），
所以改完必须 `press` 重生成，然后 `verify` —— 站点判据里"渲染出来的与内容源逐字一致"那条会盯着。

## 五、改完的验收

```bash
node ../skillpress/tools/press.mjs --check             # 内容源与生成物一致
node ../skillpress/tools/run-js.mjs audit             # 上色的闸门（改配色/色号后必跑）
```

实例里 `npm run build` → `npm run serve` 看效果；要机器判据就跑 `verify`
（它要求 `dist/bundle.js` 已经在，见 `references/make-a-site.md`）。

⚠️ **别手改生成物**（`content/content.generated.mbt`）：它的新鲜度由 `press --check` 保证，
手改之后下一次 `press` 就把你那次改动抹掉，而你会先经历一段"改了没反应"的困惑。
